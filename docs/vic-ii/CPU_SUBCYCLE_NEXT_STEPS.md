# CPU sub-cycle deep dive — findings + next steps

Drafted 2026-05-19 after the VICE-shaped Phase 1-9 architecture work.

## Key finding: the "CPU sub-cycle floor" name is misleading

JaC64's CPU model ALREADY matches VICE's:

- `CPU.VICE_CYCLE_ACCESS_PHASE` is locked-on (`static final` constant).
- `writeByte` / `loadByte` apply the bus access at `cycles=N`, then
  `clockIncAfterCurrentCycleAccess()` does `cycles++` + `schedule(N+1)`.
- `schedule(N+1)` triggers `chips.clockPhi2(N+1)` = VIC's per-cycle work
  for the next cycle.

VICE's pattern (CPU writes → `CLK_INC` → `vicii_cycle()` for next clk)
is identical. A CPU write at clk=N is visible to VIC cycle N+1 in both.

Phase K iter#16 (commit `d4aa5e7`) verified this empirically on
modesplit: `$D011` writes commit at IDENTICAL `(line, cyc)` in JaC64
and VICE traces.

**There is no CPU Phi1/Phi2 work left to do.** The historical
`project_cpu_subcycle_floor.md` framing was based on Phase J trace
artifacts that were later fixed (see `project_phase_j_trace_bug.md`).

## Where the remaining wins live

### A. Colorsplit retroactive-paint fix (highest leverage: -1428 cells)

`project_colorsplit_deep_dive.md` identifies the exact bug:
`applyD021CurrentCycleColor` repaints any pixel matching `oldColor`
with `newColor` — including FG pixels — when color RAM=0 and old
$D021=0. Fix is to gate retroactive paint on `renderBuf` codes
(only repaint VC_D021/VC_D02X_EXT codes), but a previous attempt
showed renderBuf is all-zero at the moment applyD021 fires. The
real fix needs to track WHICH renderBuf slots are background-derived
vs foreground-derived. Multi-day work but tractable.

### B. Screenpos reference mismatch (high leverage: -2857 cells if solvable)

The shift=-16 paint base aligns with VICE's `cycle_get_xpos`
quantization, but screenpos's `*-8565early.png` reference renders at
shift=-8's paint position. Per `project_colorlatency_hoxs64.md`, the
`*-8565early.png` references were generated by hoxs64 (per VICE-testprogs
readme.txt), not VICE x64sc. Options:
1. Generate a true-VICE reference for screenpos using local patched
   x64sc and add it to the comparison.
2. Accept the regression as a "reference convention" cost.

### C. Mode-pipe sub-pixel precision (modesplit, vicii_reg_timing, etc.)

VICE's `vmode11_pipe` updates have specific semantics:
- color_latency=1 (6569): `|=` at pix 4 (rising), `&=` at pix 6 (falling)
- color_latency=0 (8565): assignment at end of cycle

JaC64's `ViceDrawCycle.drawGraphics8` matches both per `colorLatency`
field. Empirically, flipping `colorLatency` makes <10 cell difference
in the current architecture — both modes leave similar residuals.

The pixel-4 OR vs pixel-6 AND has 2-pixel granularity. When a $D016
mid-line write lands BETWEEN pix 4 and pix 6, the rising-edge OR
captures the new value but the falling-edge AND clears it. VICE
handles this same way. No deviation found in code review.

The residual may be in **WHICH PIXEL within the cycle** the CPU write
sequences relative to draw_graphics8(0..7). Need per-pixel trace
showing write commit pixel vs current architecture's pixel observation.

### D. RMW dummy-write semantics (rmwtest 752)

VICE has specific timing for RMW dummy-write of $D019 (clears IRQ
flag with old value during cycle N, then writes new value during
cycle N+1 of the same instruction). JaC64 has `viceD019Phi2`
removed in commit `ce3f76e` — both dummy and final writes follow
uniform path. May not exactly match VICE.

Need to trace a specific RMW sequence (e.g., DEC $D019 or LSR $D019)
and check that the dummy-write at the third cycle and final-write at
the fifth cycle have correct visibility.

## Architecture state (post f18dfb9)

JaC64's per-cycle path now mirrors VICE's `vicii_draw_cycle` exactly:
- Order: gfx → sprites (fresh in-cycle priBuffer + collisions) →
  composite → border → colors
- Paint base + sprite trigger both at Phi1(N)-quantized xpos
- `cycle_flags_pipe` for sprites (PREV cycle's flags)
- 6569/8565 sprite mc-bits split by `color_latency`
- CPU `VICE_CYCLE_ACCESS_PHASE` locked on

The structural port is complete. Further reductions are TEST-SPECIFIC
bug hunts, not architecture refactors.
